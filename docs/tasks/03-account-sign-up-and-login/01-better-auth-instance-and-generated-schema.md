# 01 — The Better Auth instance, its generated schema and the migration

**Roadmap:** [03](../../roadmap/03-account-sign-up-and-login.md) · **Scope:** back-end · **Depends on:** —

## Context

- Better Auth owns the `user`, `session`, `account` and `verification` tables. No
  other slice in this item can be written until they exist and the instance that
  generates them is configured.
- `auth.md`'s Commands table names `make api-auth-schema` and nothing in the
  `Makefile` defines it. This slice is where that target is written.
- The generated schema file is committed unedited. Editing it means the next
  regeneration silently reverts the edit, so drift is checked instead.
- `naming.md` rule 14: `account` is Better Auth's own table name and the game's
  word for a person is *player*. Nothing the library generates is renamed here.
- `apps/api/src/modules/auth/` already has its four empty layer folders from
  [`01`](../../roadmap/01-the-api-foundation.md); `system` is the pattern for
  where a module's Drizzle schema lives.

## Technical details

- **API stack** — install `better-auth` 1.7.2 in `apps/api` on the Drizzle
  adapter, sessions in this project's own Postgres, no community Nest adapter;
  `stack-api.md` rules 26–28.
- **Auth** — build the instance in `auth/infrastructure/`: e-mail and password
  on, no mail sender, verification and reset switched off (`FR.1.2`, `FR.1.5`).
- **Auth** — password bounds pinned to 8–128 with no composition rules
  (`FR.1.3`); session `expiresIn` 30 days with the refresh window extending it on
  activity (`FR.2.2`, `auth.md` rule 31).
- **Back-end** — the instance is infrastructure: nothing in `domain`,
  `application` or `entrypoint` imports `better-auth`;
  `architecture-api.md` rules 19–24.
- **Auth** — every `better-auth` import stays inside
  `apps/api/src/modules/auth`, so an upgrade or a swap is one folder rather than
  a grep; `auth.md` rule 1. This slice is where that boundary is set, and task
  `05` is where it is first pulled on.
- **Back-end** — add the `api-auth-schema` target to the `Makefile`, run it into
  the auth module's Drizzle schema folder mirroring `system`'s
  `infrastructure/database/schema` layout, and commit the output unedited;
  `auth.md` rule 5.
- **Back-end** — produce the migration with `drizzle-kit` through
  `make migrate-generate`, and commit it alongside the schema.

## Acceptance criteria

- [ ] `(integration)` `make migrate` on a reset database applies the new migration and creates `user`, `session`, `account` and `verification`
- [ ] `(integration)` `make api-auth-schema` regenerates the committed schema file byte-identical, so a drift check can run in `make check`
- [ ] `(unit)` the instance enables e-mail and password with a minimum length of 8 and a maximum of 128, and registers no mail sender
- [ ] `(unit)` e-mail verification and password reset are both off
- [ ] `(unit)` the session lasts 30 days and its refresh window extends the expiry on activity
- [ ] `(integration)` a password written through the instance is stored hashed, and the plain text appears in no column
- [ ] `(unit)` no file outside `apps/api/src/modules/auth` imports `better-auth`, checked the way `test/module-structure.spec.ts` already checks the other boundaries
